# ADR-002: Foundation administration, paging, and worker verification

Status: Accepted, 15 September 2026.

Roster lists use ascending UUID keyset cursors, 20 items per page, with a 21st row detecting continuation. Names remain editable without changing cursor position. Classes and people have independent URL cursors. Enrollment totals are aggregated for visible classes under RLS; authorization of mutations uses a direct class lookup, never a list page. Admin pages include disabled profiles so access can be restored. Forms accept IDs beyond the currently displayed suggestions.

Admins may create accounts with an initial password, edit display names/roles, and disable/reactivate accounts in their own organization. No invitation email is sent. Account creation requires a server-only Supabase service-role key used solely for Auth creation. A session-scoped RPC first reserves the account details. The server-only Auth adapter calls a completion RPC immediately after Auth creation; the database trigger remains a direct-database safeguard. The completion RPC creates the profile/student row/audit atomically with the reservation; organization and role come from the reservation, never client user metadata. Retries reuse a request UUID and reject conflicting details; completed requests return their existing account. Passwords are never persisted in application tables or audit. Changing a password after a completed provisioning request is not a password reset.

Account writes require an active admin with a signed Auth session with an `auth_time` claim within 15 minutes. Refreshing a JWT does not extend this window. Admins cannot change their own role or disable themselves. Optimistic profile versions reject stale edits. Role changes are blocked while active class/guardian/enrollment relationships require the old role. Disabling a student or parent revokes their active relationships; reactivation does not restore them implicitly. Disabling a teacher blocks their access but preserves their classes for school administration. Audit includes before/after values and a reason for account edits.

Deno is pinned as a workspace development tool. Shared packages remain source imports with explicit .ts extensions, an Edge import map, strict typechecking, and permission-free compatibility tests. The worker foundation exposes an authenticated health probe only; queue consumption and AI calls belong to Week 3 and are not simulated as completed grading.

Bootstrap verification uses an isolated source copy excluding generated files and secrets, a frozen install, a dedicated local Supabase project/port range, clean migrations and synthetic roles, web and worker health checks, and four-role browser smoke. Resets are limited to that disposable project. Record actual timing and any unavailable checks rather than claiming a clean-clone result from an existing working database.
